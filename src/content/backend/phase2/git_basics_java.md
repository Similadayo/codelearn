# Git Basics — Commits, Branches & Merging in Java Backend Projects

Git is the backbone of modern software development workflows. In backend engineering, clean commit history, thoughtful branching, and reliable merge practices enable teams to ship features with confidence, roll back changes when needed, and trace every change to its origin. This lesson focuses on Commits, Branches, and Merging using a Java project as the running example, illustrating practical commands, code integration, and conflict resolution.

## 1. Getting Started: Initialize a Java Project and Git Repository

To work with Git effectively in a Java backend project, start with a clean repo and a sensible project skeleton. This section shows creating a minimal Java app, initializing Git, and adding a .gitignore to avoid tracking build artifacts.

Code block 1:
```
mkdir -p backend-java/src/main/java/com/example/app
cd backend-java
git init
```

Code block 2:
```
printf 'package com.example.app;\n\npublic class App {\n    public static void main(String[] args) {\n        System.out.println("Hello, Git!");\n    }\n}\n' > src/main/java/com/example/app/App.java
```

Code block 3:
```
printf 'target/\n*.class\n*.jar\n.gradle/\nbuild/\n.idea/\n/.settings/\n' > .gitignore
```

Code block 4:
```
git add -A
git commit -m "chore: initial Java project skeleton"
```

### Line-by-line explanation

Block 1:
- mkdir -p backend-java/src/main/java/com/example/app: Create the Java project directory structure in a conventional Maven/Gradle layout.
- cd backend-java: Change into the project root to initialize Git there.
- git init: Create a new, empty Git repository in the current directory.

Block 2:
- printf 'package com.example.app;...': Write a minimal App.java source file with a conventional package and a simple main method that prints a message.
- > src/main/java/com/example/app/App.java: Redirection to create the file with the specified content.

Block 3:
- printf 'target/...' > .gitignore: Create a .gitignore that excludes build outputs, IDE metadata, and common Java artifacts.
- The patterns cover common directories/files generated by builds and IDEs.

Block 4:
- git add -A: Stage all new/modified files for commit.
- git commit -m "chore: initial Java project skeleton": Create the initial commit with a descriptive message.

## 2. Tracking Changes with Commits

Good commit discipline makes history readable and rollback safer. This section demonstrates updating source code, staging changes, making focused commits, and using amend when necessary.

Code block 1:
```
printf 'package com.example.app;\n\npublic class App {\n    public static void main(String[] args) {\n        System.out.println("Hello, Git! v2");\n    }\n}\n' > src/main/java/com/example/app/App.java
```

Code block 2:
```
git add src/main/java/com/example/app/App.java
git commit -m "feat: update App greeting to v2"
```

Code block 3:
```
git log --oneline --graph --decorate --all
```

Code block 4 (amending the previous commit):
```
git commit --amend -m "feat: update App greeting to v2 (amended)"
```

### Line-by-line explanation

Block 1:
- Rewrites App.java to update the greeting to "Hello, Git! v2", illustrating a code change on the default branch.

Block 2:
- git add src/main/java/com/example/app/App.java: Stage the modified App.java for commit.
- git commit -m "feat: update App greeting to v2": Create a new commit describing the feature-like change.

Block 3:
- git log --oneline --graph --decorate --all: Display a concise, readable history with branch pointers and commits for context.

Block 4:
- git commit --amend -m "...(amended)": Change the previous commit message (and/or content if you staged more changes) without creating a new commit, keeping history compact.

## 3. Branching Strategy and Lifecycle

Branches enable isolated work streams (features, experiments) and safer collaboration. This section covers creating feature branches, making changes on them, and preparing them for integration.

Code block 1:
```
git checkout -b feature/auth
```

Code block 2:
```
printf 'package com.example.app;\n\npublic class AuthService {\n    public boolean isAuthenticated(String user) {\n        return user != null && !user.isEmpty();\n    }\n}\n' > src/main/java/com/example/app/AuthService.java
```

Code block 3:
```
printf 'package com.example.app;\n\npublic class App {\n    public static void main(String[] args) {\n        System.out.println(\"Hello, Git! (feature/auth)\");\n    }\n}\n' > src/main/java/com/example/app/App.java
```

Code block 4:
```
git add -A
git commit -m "feat: add AuthService and feature message in App"
```

Code block 5:
```
git checkout main
```

Code block 6:
```
git merge --no-ff feature/auth -m "Merge feature/auth: add auth capability"
```

Code block 7:
```
git branch --all
```

### Line-by-line explanation

Block 1:
- git checkout -b feature/auth: Create and switch to a new branch named feature/auth to work on authentication-related changes in isolation.

Block 2:
- printf 'AuthService.java' content: Add a new AuthService class with a simple isAuthenticated method to illustrate a backend capability change.
- > AuthService.java: Write file with the provided content.

Block 3:
- Update App.java to reflect the feature context, e.g., printing a feature-related message, providing a quick sanity check in the main method.

Block 4:
- git add -A: Stage the new AuthService and updated App.java.
- git commit -m "feat: add AuthService and feature message in App": Create a commit representing the feature work on the new branch.

Block 5:
- git checkout main: Switch back to the main branch to plan integration.

Block 6:
- git merge --no-ff feature/auth -m "...": Merge the feature/auth branch into main and ensure a merge commit is created even if a fast-forward is possible, preserving branch history.

Block 7:
- git branch --all: List all branches (local and remote) to verify integration and current state.

Note: If main had advanced since the branch point, a true merge commit will be created. The --no-ff option forces a merge commit even in the fast-forward scenario, which is useful for preserving a visible integration point in history.

## 4. Merging Strategies, Conflicts, and Resolutions

Merging is where many teams spend time resolving conflicts and debating history shape. This section demonstrates a conflict scenario, how Git exposes conflicts, and how to resolve them cleanly.

Code block 1 (simulate conflicting changes on App.java):
```
# On main
printf 'package com.example.app;\n\npublic class App {\n    public static void main(String[] args) {\n        System.out.println(\"Hello from Main!\");\n    }\n}\n' > src/main/java/com/example/app/App.java
git add -A
git commit -m "chore: main baseline App.java (for conflict-demo)"
```

Code block 2 (on feature/conflict-demo branch):
```
git checkout -b conflict-demo
printf 'package com.example.app;\n\npublic class App {\n    public static void main(String[] args) {\n        System.out.println(\"Hello from Feature: Conflict!\");\n    }\n}\n' > src/main/java/com/example/app/App.java
git add -A
git commit -m "feat: conflicting change to App.java on feature branch"
```

Code block 3 (attempt to merge and trigger conflict):
```
git checkout main
git merge conflict-demo
```

Code block 4 (example of a merge conflict in App.java):
```
<<<<<<< HEAD
        System.out.println("Hello from Main!");
=======
        System.out.println("Hello from Feature: Conflict!");
>>>>>>> conflict-demo
```

Code block 5 (resolving the conflict and finalizing the merge):
```
printf 'package com.example.app;\n\npublic class App {\n    public static void main(String[] args) {\n        System.out.println("Hello from Main!");\n    }\n}\n' > src/main/java/com/example/app/App.java
git add src/main/java/com/example/app/App.java
git commit -m "chore: resolve merge conflict in App.java"
```

### Line-by-line explanation

Block 1:
- Creates a main baseline App.java with a print message to establish a known state for a merge conflict.

Block 2:
- Creates a feature branch conflict-demo and changes App.java to print a different message.
- The new App.java represents an incompatible change intended to be merged back into main.

Block 3:
- Switch back to main and attempt to merge conflict-demo into main. Git detects conflicting changes in App.java.

Block 4:
- The conflict markers <<<<<<<, =======, >>>>>>> indicate the two competing versions:
  - HEAD block shows the version on main.
  - The rival block (after =======) shows the version from the feature branch.
- This block documents how Git presents the conflict content in the file.

Block 5:
- Resolve the conflict by choosing the desired final content (here we preserved the main version).
- Write the resolved App.java, stage it, and commit the resolution to complete the merge.

Notes on strategies:
- Merge commit (default): preserves a record of the merged branch.
- Fast-forward merge: moves the branch pointer forward without creating a new merge commit when there are no new commits on the base branch since the branch point.
- No-fast-forward (--no-ff): forces a merge commit to preserve an explicit integration point even if a fast-forward would be possible.
- Squash merge (--squash): combines all changes from the branch into a single commit on the target branch (no merge commit produced on the target).

## 5. Why This Matters In Real Systems

- Traceability: Every change is recorded as a commit with a message, author, and timestamp. This enables auditing, rollbacks, and reproducible builds.
- Collaboration: Branching models (feature branches, short-lived fixes, release branches) enable parallel work with clear ownership and review workflows.
- Stability: Merges with well-defined strategies (no-ff, squash, etc.) help maintain a readable history and predictable release notes.
- Conflict resolution discipline: Early and deliberate conflict resolution reduces risk in production deployments and helps maintain code quality.
- Build and release pipelines: Git history is often tied to CI/CD pipelines. Clear commit messages and merge commits improve automated testing, deployment, and rollback decisions.

Part E — Cleanup and reflection
- Push your branches to a remote (if you have one) and open a mental model of how your history would look in a real team setting.
