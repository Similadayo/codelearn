## 1. Core Concepts: PHP Modules, Packages, and Dependency Management

Understanding the relationships between modules, packages, and dependencies is foundational. Modules are units of code organization (classes, functions, and namespaces). Packages bundle modules for reuse and distribution. Dependency management (with Composer) resolves and autoloads code from external packages, tracks versions, and ensures consistent builds.

Code examples demonstrate:
- A simple PSR-4 autoloaded package
- How to load and use it in an application
- Basic composer.json configuration to enable autoloading

### Code: A small PSR-4 package and usage

```php
// src/MyApp/Tools/Greeter.php
<?php
namespace MyApp\Tools;

class Greeter {
    public function greet(string $name): string {
        return "Hello, " . $name . "!";
    }
}
```

```json
// composer.json (root project)
{
  "name": "example/app",
  "description": "Demonstration app using PSR-4 autoload",
  "require": {},
  "autoload": {
    "psr-4": {
      "MyApp\\": "src/"
    }
  }
}
```

```php
// public/index.php
<?php
require __DIR__ . '/../vendor/autoload.php';

$greeter = new \MyApp\Tools\Greeter();
echo $greeter->greet("World");
```

### Line-by-line explanation

- src/MyApp/Tools/Greeter.php
  - namespace MyApp\Tools;: Declares the PHP namespace for the class to avoid name collisions.
  - class Greeter { ... }: Defines the Greeter class.
  - public function greet(string $name): string { ... }: Declares a method that returns a formatted greeting.
  - return "Hello, " . $name . "!";: Builds and returns the greeting string.
- composer.json
  - "autoload": { "psr-4": { "MyApp\\": "src/" } }: Configures Composer to map the namespace MyApp\ to the src/ directory, enabling autoloading.
- public/index.php
  - require __DIR__ . '/../vendor/autoload.php';: Loads the Composer autoloader so classes in MyApp\ can be instantiated automatically.
  - $greeter = new \MyApp\Tools\Greeter();: Instantiates the Greeter class using its fully-qualified namespace.
  - echo $greeter->greet("World");: Calls the method and prints the greeting.

### Line-by-line explanation

- The class is defined under the MyApp\Tools namespace to avoid conflicts with similarly named classes.
- The Greeter::greet method accepts a name and returns a formatted string.
- The root composer.json declares an autoload mapping, so any class under MyApp\ will be located in src/.
- The public/index.php script relies on the generated autoloader to load Greeter without manual include/require statements.
- Running composer install (with a proper vendor dir) enables the autoloader, and public/index.php prints "Hello, World!".

## 2. Dependency Management with Composer: Installing and Autoloading

Composer is PHP's de facto dependency manager. It resolves libraries, downloads them, and generates an autoloader. This section shows how to initialize a project, add a dependency, and use autoloading to consume a library (e.g., a logging library).

### Code: Composer setup and a simple usage example

```bash
# Initialize a new PHP project (no prompts)
composer init -n

# Add a third-party dependency (Monolog for logging)
composer require monolog/monolog:^2.0
```

```php
// example-usage.php
<?php
require __DIR__ . '/vendor/autoload.php';

use Monolog\Logger;
use Monolog\Handler\StreamHandler;

$log = new Logger('app');
$log->pushHandler(new StreamHandler(__DIR__ . '/app.log', Logger::INFO));

$log->info('This is an informational message.');
```

### Line-by-line explanation

- composer init -n: Creates a basic composer.json without interactive prompts.
- composer require monolog/monolog:^2.0: Adds Monolog as a dependency and updates composer.lock.
- require __DIR__ . '/vendor/autoload.php';: Loads the autoloader generated by Composer.
- use Monolog\Logger; use Monolog\Handler\StreamHandler;: Imports Monolog classes with short names.
- $log = new Logger('app');: Creates a logger instance named "app".
- $log->pushHandler(new StreamHandler(__DIR__ . '/app.log', Logger::INFO));: Attaches a handler to write logs to app.log at INFO level.
- $log->info('This is an informational message.');: Writes an informational log entry.

## 3. Namespaces and Autoloading: PSR-4 Best Practices

Namespaces organize code and prevent collisions, while autoloading eliminates manual requires. PSR-4 autoloading maps a PHP namespace to a directory. This section expands on best practices to keep packages interoperable across teams.

### Code: PSR-4 autoloading in a library and consuming project

```json
// packages/greetings/composer.json (library package)
{
  "name": "acme/greetings",
  "type": "library",
  "autoload": {
    "psr-4": {
      "Acme\\Greetings\\": "src/"
    }
  }
}
```

```php
// packages/greetings/src/Greeter.php (library)
<?php
namespace Acme\Greetings;

class Greeter {
    public function hi(string $name): string {
        return "Hi, " . $name . "!";
    }
}
```

```json
// app/composer.json (consumer project using library)
{
  "repositories": [
    { "type": "path", "url": "../packages/greetings" }
  ],
  "require": {
    "acme/greetings": "*"
  },
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  }
}
```

```php
// app/src/index.php
<?php
require __DIR__ . '/vendor/autoload.php';

use Acme\Greetings\Greeter;

$g = new Greeter();
echo $g->hi("PHP Student");
```

### Line-by-line explanation

- Acme\Greetings\Greeter.php
  - namespace Acme\Greetings;: Defines the library namespace.
  - class Greeter { public function hi(string $name): string { ... } }: Simple greeting method.
  - return "Hi, " . $name . "!";: Returns a greeting string.
- library composer.json
  - "autoload": { "psr-4": { "Acme\\Greetings\\": "src/" } }: Maps the library namespace to its source directory.
- consumer app composer.json
  - "repositories": [{ "type": "path", "url": "../packages/greetings" }]: Declares a local path repository for the library.
  - "require": { "acme/greetings": "*" }: Requires the library package.
  - "autoload": { "psr-4": { "App\\": "src/" } }: Sets up autoloading for the app namespace.
- app/src/index.php
  - require vendor/autoload.php: Loads Composer autoloader.
  - use Acme\Greetings\Greeter;: Imports library class.
  - $g = new Greeter(); echo $g->hi("PHP Student");: Uses the library and prints the greeting.

## 4. Local Packages and Path Repositories: Developing in Monorepos or Local Workflows

Local path repositories let you develop packages in parallel without publishing. This section demonstrates how to wire a local package into a consuming project for rapid iteration.

### Code: Path repository workflow example

```json
// Library: packages/greetings/composer.json (unchanged from previous section)
{
  "name": "acme/greetings",
  "type": "library",
  "autoload": {
    "psr-4": {
      "Acme\\Greetings\\": "src/"
    }
  }
}
```

```json
// App: app/composer.json (using path repository)
{
  "repositories": [
    { "type": "path", "url": "../packages/greetings" }
  ],
  "require": {
    "acme/greetings": "*"
  },
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  }
}
```

```php
// app/src/index.php
<?php
require __DIR__ . '/vendor/autoload.php';
use Acme\Greetings\Greeter;

$greet = new Greeter();
echo $greet->hi("Developer");
```

### Line-by-line explanation

- In the library, composer.json defines a PSR-4 autoload rule for Acme\Greetings.
- In the app, the path repository is declared so composer can symlink or copy the library into vendor/.
- The consumer app autoloads all classes, including Acme\Greetings\Greeter, enabling usage without manual includes.
- The index.php demonstrates consuming the library as if it were installed from a remote package registry.

## 5. Dependency Versioning and Constraints: Semver and Stability

Version constraints determine which versions of dependencies your project accepts. Correct constraints help avoid breaking changes while enabling safe updates. This section shows best practices for semver constraints, minimum stability, and lockfiles.

### Code: Example composer.json with best practices

```json
{
  "name": "example/app",
  "description": "Dependency management demo",
  "require": {
    "monolog/monolog": "^2.0",
    "acme/greetings": "^1.0"
  },
  "minimum-stability": "stable",
  "prefer-stable": true
}
```

### Line-by-line explanation

- "monolog/monolog": "^2.0": Accepts any 2.x version that is backward-compatible with 2.0, but will not auto-upgrade to 3.x without manual change.
- "acme/greetings": "^1.0": Accepts any 1.x version compatible with 1.0, enabling updates within the 1.x line.
- "minimum-stability": "stable": Ensures only stable releases are used unless explicitly overridden.
- "prefer-stable": true: Encourages stable versions when a choice exists between stable and development builds.

## X. Common Beginner Mistakes

- Mistake 1: Not using Composer autoload; manual requires everywhere
  Bad:
  ```php
  // index.php (bad)
  <?php
  require 'src/MyApp/Tools/Greeter.php';
  $g = new \MyApp\Tools\Greeter();
  ```
  Good:
  ```php
  // index.php (good)
  <?php
  require __DIR__ . '/vendor/autoload.php';
  $g = new \MyApp\Tools\Greeter();
  ```
- Mistake 2: Failing to namespace classes; global class name collisions
  Bad:
  ```php
  // Greeter.php (bad)
  class Greeter {
      public function greet($name) { return "Hello, ".$name; }
  }
  ```
  Good:
  ```php
  // src/MyApp/Tools/Greeter.php (good)
  <?php
  namespace MyApp\Tools;

  class Greeter {
      public function greet(string $name): string {
          return "Hello, ".$name;
      }
  }
  ```
- Mistake 3: Overly strict or invalid version constraints
  Bad:
  ```json
  {
    "require": {
      "monolog/monolog": "2.x"
    }
  }
  ```
  Good:
  ```json
  {
    "require": {
      "monolog/monolog": "^2.0"
    }
  }
  ```
- Mistake 4: Not locking dependencies; ignoring composer.lock
  Bad:
  - Do not commit composer.lock; builds drift across environments
  Good:
  - Commit composer.lock and run composer install in CI to reproduce builds exactly

## Y. Why This Matters In Real Systems

- Reproducible builds: Composer.lock ensures the same dependency graph across teams, environments, and deployments.
- Security and compliance: Centralized dependency management allows scanning for vulnerabilities and updating libraries in a controlled way.
- CI/CD pipelines: Automating composer install with production optimizations (e.g., --no-dev, --optimize-autoloader) reduces cold-start times and memory usage.
- Multi-package ecosystems: Local path repositories and proper autoloading enable modular architectures, microservices, and monorepos without publishing to a public package registry.
- Version discipline: Semver constraints help teams plan upgrades, test compatibility, and minimize breaking changes.
